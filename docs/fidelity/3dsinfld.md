# 3DSINFLD — the 3D sinus field (COMAN)

`COMAN/MAIN.C` (228 lines) over `COMAN/ASM.ASM` (238 — `inittwk`, `docol`,
`docopy`, `setpalarea`), `COMAN/THELOOP.INC` (5,230, generated by
`COMAN/DOLOOP.C`) and the two linked wave tables `W1DTA.BIN`/`W2DTA.BIN`.
The transcription is `bins/secondreality/src/parts/coman.rs`; its unit tests
are beside it and the process-level test is `bins/secondreality/tests/
coman.rs`.

The part is block 3's sixth (`shell.rs`'s `PART_ORDER`), reached after
RAYSCRL, and is registered under the demo's own name, `"3dsinfld"` — not a
legal Rust identifier, which is why the module is `coman.rs`.

**There is no boot anchor.** The reference's picture enters in the window
`(15000, 15100]` (`reference-indices.md` §16) and the part marks no start
frame, so a `--part 3dsinfld` run numbers its own frames from zero:
`index_origin: "part"`, `anchor: null`.

## 1. The screen: mode 13h with chain-4 off

`MAIN.C:118-126` is `dis_partstart(); mov ax,13h; int 10h`, and `inittwk`
(`ASM.ASM:36-78`) then takes CRTC `0x14 = 0` (`mov ax,00014h`), CRTC
`0x17 = 0xE3` (`mov ax,0e317h`), the sequencer's memory mode to 6
(`mov ax,0604h` — **chain-4 off**) and the map mask to all four planes
(`mov ax,0f02h`). It never writes CRTC `0x13`, so the offset stays mode
13h's 40 words: **80 plane bytes a scanline**.

In the emulator's unchained handler a CPU byte address names four plane
bytes (`VGA_UnchainedVGA_Handler` stores at `4*addr + plane`), and the
`M_VGA` display reads them straight back, one linear byte a pixel. The port
keeps that interleaved 256 KB image and composes the displayed 320×200 window
from the page in force, 320 linear bytes a scanline.

`docopy` writes each vbuf row under two map masks (`ASM.ASM:190-207`):

```text
	mov	dx,3c4h
	mov	ax,0302h
	out	dx,ax
	zzz=0
	REPT	20
	mov	eax,ds:[si+zzz]
	mov	es:[di+zzz],eax
	zzz=zzz+4
	ENDM
	mov	dx,3c4h
	mov	ax,0C02h
	out	dx,ax
	zzz=0
	REPT	20
	mov	eax,ds:[si+zzz+80]
	mov	es:[di+zzz],eax
	zzz=zzz+4
	ENDM
```

The first block runs with map mask `0x03` (planes 0 and 1) and the second
with `0x0C` (planes 2 and 3), so the four displayed pixels of one plane address are `(a, a, b, b)` —
planes 0 and 1 carry the same byte and planes 2 and 3 the other. The vbuf
row's first 80 bytes are the *even* terrain columns (`b=(a&1)*80+(a>>1)+…`,
`MAIN.C:91`) and its second 80 the odd ones, so the 160-wide buffer becomes
320 pixels with **each column shown twice**, in column order. The doubling
is `docopy_doubles_each_column_and_starts_below_its_eighteen_row_clear`.

**The 18-row clear.** The source's destination is not what its first line
suggests:

```text
	mov	si,60*160
	mov	di,52*80
	mov	cx,18*80/4
	xor	eax,eax
	rep	stosd
	mov	cx,140
```

`rep stosd` advances `di` over the 1,440 bytes it clears, so the 140-row copy
begins at destination row **70**, not 52: rows 52..69 stay the black band the
clear writes. The picture is 140 rows from vbuf row 60 at rows 70..209, so
rows 200..209 never show and vbuf's own last 10 rows are never displayed.
The port performs both steps in that order (`docopy`), and the shift unit is
`5*startrise` paragraphs = 80 plane addresses = **one row** a unit
(`docopy_shifts_by_one_row_a_startrise_unit`).

After the copy, `ASM.ASM:216-229` clears vbuf rows 68..97 (30 rows,
`cx = 30*160/4/4` with four `stosd`s a pass). That clear is *after* the
copy, so it is seen by the next frame; rows 60..67 and 98..199 are not
cleared there.

The formula walks entries **223 down to 8**; the `*9/6` pass brightens
entries 0..239 and clamps at 63; the dark-red bar writes entries 255 down to
232; entry 0 is forced black; the last loop overwrites entries 240..255 from
`combg`.

The port's pins (`the_palette_is_the_formula_with_the_bar_and_the_unreachable_overrun`):

| entry | source `a` | value (6-bit) |
|---|---|---|
| 0 | — | `(0, 0, 0)`, forced black |
| 8 | 255 | `(1, 0, 0)` |
| 37 | 220 | `(19, 0, 16)` — the red diamond's peak |
| 100 | 146 | `(0, 27, 54)` |
| 223 | 0 | `(0, 63, 63)` |
| 232..239 | 23..16 | the dark-red bar, `((a-4)/2, 0, 0)` |
| 240..255 | — | the `combg` overrun, below |

`SIN1024.INC` is the part's own 1,024-word table, `the_sine_table_is_the_
sources_own_1024_words` rebuilds it from the file.

### The unlinked background

`COMBG.UH`, `COMBG.X` and `COMBG.LBM` are **not in the link**:

```text
$ grep -n "asm_f\|^c.exe\|link" upstream/SecondReality/COMAN/MAKEFILE
6:asm_f	= /ML /m2 /s /JJUMPS
11:	tasm $(asm_f) $<
16:c.exe : $(objs)
17:	link /E $(objs)+$(dobjs),c.exe,nul;
$ grep -n "PXLSUX" upstream/SecondReality/COMAN/ASM.ASM
143:IFDEF PXLSUX
```

`objs` is `main.obj asm.obj theloop.obj ..\dis\disc.obj` and `dobjs` the
four wave-table objects; `asm.obj` holds `_combguse` (a `90*160 dup(0)`
BSS array) and no `combg` data. The C global is `char combg[16]`
(`MAIN.C:8`), so every index the source uses is an **overrun**:

- the palette's `palette[x] = combg[16+x]` for `x = 720..767` reads
  `combg[736..783]` — 48 bytes past a 16-byte array;
- the `combguse` fill (`MAIN.C:166-176`) reads
  `combg[x*4+y*320+768+16]`, up to `combg[29582]` at `x = 79, y = 89` (the second loop adds 2 instead of 0).

`combguse` is read only by `docopy`'s `IFDEF PXLSUX` half (`ASM.ASM:143-172`),
and `tasm $(asm_f)` defines no `PXLSUX`: **there is no background**. The
overrun's destination is unreachable as well — the ray march's colour is
`((bx + 140 - j/8) & 0xFF) >> 1`, never above 127, so DAC entries 240..255
never reach the screen. The port keeps the 16-byte array, models the palette
read at the source's own indexes (all beyond the array, returning the
model's zeroes), and does not draw the dead background. Both facts are
tests: the palette test's exhaustive `i16` colour sweep reaches 127 and no
more, and `docopy`'s test asserts rows 0..51 (where the `PXLSUX` half wrote)
stay zero.

### The wave tables

`CALCW12` is off (`MAIN.C:6` `#define noCALCW12`), so `MAIN.C:212-213` is
the live half: `wave1 = w1dta; wave2 = w2dta`. Both files are 32,768 signed
little-endian words:

```text
$ wc -c assets/COMAN/W1DTA.BIN assets/COMAN/W2DTA.BIN
65536 assets/COMAN/W1DTA.BIN
65536 assets/COMAN/W2DTA.BIN
```

`the_wave_tables_are_the_linked_sixty_four_kilobyte_ints` asserts the sizes
and the signed ranges: `W1DTA` **−33..41**, `W2DTA` **−56..63**. The
generator's `CALCW12` half — the sine synthesis and the `w1dta.bin` dump

`halloc(16384,4)` (`MAIN.C:165`) is the 64 KB vbuf; `inittwk`'s `rep stosw`
and `memset(vram,0,64000)` clear the video memory.

## 3. `doit`, and the tick model

`MAIN.C:45-116`:

```text
	int	startrise=160,frepeat=1;
	…
	int	frame=0;
	…
	cameralevel=-270;
	dis_waitb();
	while(!dis_exit() && dis_musplus()<0);
	while(!dis_exit() && frame<4444)
```

`xw`/`yw` are copies made **before** the column loop and never updated in
it: `xwav`/`ywav` change at `a == 80` for the *next* frame. The port's first
reading updated them mid-loop and matched the reference's left half only; the
process test's 15500 comparison pins the source's order (the right half's
curvature is the difference).

`flip` selects the page the beam shows and copies into the other:
`0x0C = 0x80` is display start `0x8000` (`a800`) while the copy fills
`a000`, and `0x0C = 0x00` the reverse. A picture is therefore first shown by
the *next* iteration, two vblanks after it was drawn —
`the_two_pages_alternate_and_the_display_lags_one_iteration`.

### `dis_waitb` and the measured tick

`DIS/DISINT.ASM:158-183`'s INDEMO arm waits for `copperframecount` to move
and returns the count since the previous call, clearing it:

```text
waitb_1 PROC NEAR
        call    checkkeys
        IFDEF INDEMO
        sti
        mov     ax,cs:copperframecount
@@v:    cmp     cs:copperframecount,ax
        je      @@v
@@q:    mov     ax,cs:copperframecount
        mov     cs:copperframecount,0
        ELSE
        …
```

One render iteration costs two of them (the reference's picture changes every
second boot frame, §6), so `frame += (frepeat = dis_waitb())` advances the
source's counter two per render and the inner body runs twice. The one other
wait is the frame-4 upload: both bodies see `frame == 4` and each spends a
vblank, so that iteration occupies four ticks while the source's own counter
still advances two. The port's iteration ticks are therefore
`0, 2, 4, 8, 10, …` (`the_iterations_run_every_second_tick_and_the_frame_four_waits_add_two`).

## 4. `theloop` — the swapped 16.16 ray march

`THELOOP.INC` is generated: `DOLOOP.C`'s `wflip` swaps the halves of a 32-bit
value,

```text
long	wflip(unsigned long l)
{
	long	m,lo,hi;
	lo=l&0xffff;
	hi=l>>16;
	m=(lo<<16)+hi;
	return(m);
}
```

so the ray state is 16.16 with the **integer part in the low word** and the
fraction in the high one. The direction starts at
`firstraydir = -(200-horizony)*2560` with `horizony = 70`, i.e.
`-(130*2560) = 0xFFFAEC00`, swapped to `0xEC00FFFA` (`THELOOP.INC:42`); the
integer half is `-6` and the fraction `0xEC00`.

The entry (`THELOOP.INC:31-52`):

```text
theloop PROC FAR
mov cs:theloop_xsina1,cx
mov cs:theloop_ysina1,dx
add cx,cx
mov cs:theloop_xsina2,cx
add dx,dx
mov cs:theloop_ysina2,dx
mov cs:theloop_heigth,ax
mov ax,cs
mov ds,ax
xor eax,eax
mov ecx,0EC00FFFAh
_@seek0:
add si,ds:theloop_xsina1
mov bx,fs:[si]
add di,ds:theloop_ysina1
add bx,gs:[di]
add bx,-240
cmp ax,bx
jge short _@seeko0
lea dx,[bx+140]
shr dl,1
_@hit0:
```

and the unrolled labels are `0..63` and then every second index to 190; the
`add bx,<k>` constants are `zwave[j] - 240` with
`zwave[j] = (int)(16.0*sin(j*2*pi*3/192))`, the colour offset is
`140 - j/8`, and the hit step is `wflip(j*2560)`.
`the_zwave_is_the_generators_three_sines_at_the_labels_it_emits` reads all
128 emitted constants out of the shipped file and compares them.

The march is translated instruction for instruction in [`theloop`]. The
carries are the whole of it, and two are easy to get wrong:

- **`add eax,l; adc ax,0`**: the 32-bit add's carry out of bit 31 must land
  in the integer half, and the *next* `add eax` must see the corrected low
  word. The port's [`add_eax`] folds it back (`theloop`'s own first draft
  did not, and the ray never climbed).
- **`_@seek1a`'s `adc ecx,0A000000h` carries the `cmp`'s CF**, which a taken
  signed `jge` does **not** clear: `0 >= -1` is true while unsigned
  `0 < 65535`, so `ax = 0, bx = 0xFFFF` jumps with CF 1. `DOLOOP.C:141`'s
  comment "carry=0 when jmp here!" is not a theorem, and the generated code
  obeys the hardware. The port reads the compare's carry.

The strongest test is
`the_ray_march_matches_the_shipped_generated_program`: it **parses the
5,230-line `THELOOP.INC` into its ~24 instruction forms and executes it** —
registers, flags and all — then compares the whole 64 KB vbuf against
[`theloop`] for five columns (including the first, at `rot2 = 4`). A
translation that disagrees on a single byte fails.

`docol` (`ASM.ASM:105-132`) masks **all four** coordinate arguments with
`not 1` before the call and passes the vbuf offset unmasked; the port's
[`docol`] does the same, so an odd `xa`/`ya` and an odd starting wave
position are impossible.

## 5. The music: the derived row, the pre-roll, the gate and the end

The demo reaches 3DSINFLD after RAYSCRL in block 3. Two filed traces cross
the part's start:

```text
$ awk -F, '$2!=p {print; p=$2}' reference/music/second3d/trace.csv | head -3

15000,91,59,37,0,6,130,0,1,6884
15038,93,0,68,0,6,130,0,2,6912
$ awk -F, '$2!=p {print; p=$2}' reference/music/second3b/trace.csv | tail -4
13479,89,0,36,0,6,130,0,0,5759
13997,90,0,37,0,6,130,0,0,6144
14514,91,0,37,0,6,130,0,1,6527
```

Order 92 is the `254` marker. The part's start window is `(15000, 15100]`
and it marks no start frame, so the row **91 is derived, not measured**:
it is the order in force where the window opens, and the window spans the
91→93 crossing. `shell::music_for_part("3dsinfld")` seeks MUSIC1 to it.

`init` pre-polls **527** frames (`Coman::MUSIC_PRE_ROLL`), the polls between
`_zplaysong(91)`'s row 0 and the gate: the 527th leaves the published row at
63 with `musplus == -1`; the engine's first tick polls the 528th and reads
order 93 row 0, `musplus == 0`, which is `MAIN.C:56`'s
`while(!dis_exit() && dis_musplus()<0)` passing. The unit test
`the_entry_pre_roll_lands_the_gate_on_order_93_row_zero` asserts both states
with the real player;
`a_mid_chain_start_does_not_pre_poll_and_blacks_the_inherited_screen` holds
the `PartCtx::music_fresh` guard.

The gate opens at tick 0, so tick 0 is the order-93 row-0 crossing the
traces put at 15031–15038. From there the part runs until `MAIN.C:59-60`'s
break, `a > -8 && a < 0`, in MUSIC1 order 96's `zplus == 1` tail: the
published row 57 first reads `musplus == -7` and the iterating part sees it
at **tick 2,014** (`the_part_ends_on_the_music_break_not_the_dead_frame_cap`).
The 4,444-frame cap is never reached.

In that tail the same inner body raises `startrise` one a vblank. The copy's
first row is `70 + startrise`, so at `startrise = 130` it is row 200 and the
screen is flat black — the reference's 17,000
(`the_terrain_rises_off_the_bottom_before_the_break`). The part itself keeps
drawing off-screen for another fifty ticks.

## 6. The reference comparison

Four keyframes, all **RGB only**. The part writes CRTC `0x0c` every frame,
and `0x80` read back as the offset register is a 256-byte plane row the
oracle's indexed read accepts — the read is racy — so no `.idx` was filed
from this part (`reference-indices.md` §16.2). The process test asserts the
files do not exist rather than implying a comparison it cannot make.

`cargo test -p secondreality --test coman` runs the four and prints each
keyframe's line. Every one is **0 differing pixels, max delta 0**:

| reference | rendered ticks | implied origin (boot − tick) |
|---|---|---|
| 15500 | 464, 465 | 15036 |
| 16000 | 966, 967 | 15034 |
| 16500 | 1470, 1471 | 15030 |
| 16800 | 1772, 1773 | 15028 |

Each keyframe is drawn on **two** consecutive ticks — `dis_waitb` returns
two vblanks a render — so the test compares both, and asserts that the tick
before and the tick two after differ: the two-frame step
`reference-indices.md` §16.3 measures for the reference's own sessions. This
is D19's support made from the rendered side; the reference holds keyframes
only.

**The mapping drifts, and it is a mapping, not an anchor.** The tick spacing
between keyframes is 502, 504 and 302 for 500, 500 and 300 boot frames, so
the implied origin moves 2, 4 and 2 frames. The reference renders at about
1.99 frames an iteration (its `dis_waitb` occasionally returns one), while
the port's model is a fixed two; the four origins are stated per keyframe.
The timing difference is registered as `APPROXIMATIONS.md` A26.

## 7. The preserved bugs

- **The unlinked background**: the `combg` overrun and the dead `combguse`
  fill, §2.
- **The palette aliasing**: the `*9/6` pass, the bar at 232..255 and the
  `combg` overwrite of 240..255, with entry 0 forced black after them all.
- **The frame-4 `setpalarea` is dead**: it re-uploads the palette already in
  force (the wait it spends is not).
- **The `frame < 4444` cap is dead** on this boot; the music break ends the
  part.
- **`cameralevel` is dead**: `MAIN.C:54` writes -270, `docol` loads it into
  `ax`, `THELOOP.INC` stores it in `theloop_heigth`, and nothing reads it.
- **`docol`'s `~1`** masks all four coordinate arguments.
- **`docopy`'s fixed bands**: the 18-row clear at row 52, the copy at row 70,
  the vbuf clear of rows 68..97.
- **The wave tables' contiguity/wrap**: `si`/`di` are 16-bit byte offsets and
  `mov bx,fs:[si]` masks the low bit; the table is the 64 KB file.
